# Body-free LLM relay contract v1

The public `relay.ts`, `relay-ledger.ts` and `relay-forward.ts` implementations define validation, forwarding and every persisted accounting field. Company applications provide a fixed policy and a Durable Object SQL adapter; they cannot add hidden request/response collection. In-memory processing necessarily sees the conversation to forward it. No bodies, tool arguments/results or secret values are persisted or logged.

## API and authentication

`GET /llm/v1/models` returns OpenAI-compatible model objects whose `id` is a company alias. `POST /llm/v1/chat/completions` requires an active installation's MyHermes access token and a fresh RFC 9449 DPoP proof for the exact URL/method. Browser Access credentials cannot invoke these endpoints. Both reject query parameters.

The POST additionally requires `MyHermes-Request-Id: <UUIDv7>`. This is an application idempotency key, independent of each DPoP proof's fresh `jti`. Scope is the owner: reuse on another installation by the same owner cannot execute twice. Internal deduplication stores HMAC-SHA-256 over a versioned domain, owner ID, request UUID and canonical validated request, using a server secret. It stores no body or unkeyed body digest, and excludes the fingerprint from every owner, administrator and duplicate receipt. A duplicate receives HTTP 409 `relay_request_registered` plus its receipt metadata; changed content receives 409 `relay_request_id_reused`. Neither executes upstream again. Rotating the fingerprint secret makes an existing request ID return the latter rejection even for unchanged content; its retained receipt still prevents another upstream execution. The relay does not replay a previous completion, including after a lost response. Clients must not automatically invent a new UUID to retry an uncertain completion.

Accepted request keys: `model`, `messages`, optional `stream`, `max_tokens`, `temperature`, `top_p`, `seed`, `stop`, `tools`, `tool_choice`, `parallel_tool_calls`, `response_format`, `reasoning_effort`. This version supports text system/developer/user/assistant/tool messages and OpenAI function tools. Text-part arrays contain only `type:text` parts. Images, audio, files, plugins, server tools, arbitrary routing/privacy/cache fields, `user`, multiple candidates and unknown keys fail closed. Function JSON Schema is data: bounded depth/size, no remote `$ref` or execution. Response formats support `text`, `json_object`, and `json_schema` with a standard `json_schema:{name,schema,description?,strict?}` wrapper. Its object schema uses the same bounded, local-reference-only validation as tool schemas. `reasoning_effort` accepts only the exact string `none` and is omitted upstream; this MVP does not offer reasoning budgets. Limits and cross-field checks are executable in the public parser. `stream_options:{include_usage:true}` is accepted for OpenAI client compatibility but stripped; current OpenRouter usage is automatic.

The response is JSON or SSE. The server adds `MyHermes-Request-Id` and `MyHermes-Server-Request-Id`. Provider errors become fixed codes; raw upstream errors are never returned or stored. No upstream response headers other than a validated generation ID enter accounting. The forwarder uses the fixed HTTPS OpenRouter URL, refuses redirects, performs one fetch and uses bounded consumer-driven streaming. Cancellation and timeouts abort forwarding but cannot prove zero provider billing.

## Metadata and accounting

`GET /v1/relay/requests/:request_id` returns the authenticated owner's receipt. Browser owner access is allowed for review. `GET /v1/admin/relay/requests?before=<row cursor>` lists at most 100 metadata rows; `GET /v1/admin/relay/usage?day=YYYY-MM-DD` returns the selected JST request-start day's totals. Admin routes require browser admin authentication and never expose conversations.

Persisted fields are governed by the standalone **relay manifest 1.3.0**, published in `monitoring/relay-manifest.v1.json`, exported as `RELAY_MANIFEST` and available to authenticated users at `GET /v1/relay/manifest`. It is separate from client-event manifest 1.0.0, whose signed offline batches remain compatible. The ledger stores sequential cursor, owner/person ID, installation ID, client/server request UUIDs, internal keyed request fingerprint (legacy SQL column `request_hash`, never projected), alias, configured and returned model/provider, immutable admission `generation_model`, generation ID, request-start JST day/time, update time, reservation, nullable native token counts/cost, execution/usage state, fixed failure code, `usage_source` (`response`, `generation` or null), and `reconciled_at`. Internal `finish_value` and `reconcile_value` are exact metadata-only idempotency receipts. `retire_after_ms` is the internal known-row retention deadline. The settings also store a monotonic `clock_floor_ms` and nullable `history_complete_since` coverage boundary. A separate `frozen` setting stops admission after an observed reservation overrun. States are `registered`, `completed`, `failed`, `cancelled`, `timeout`; usage is `unknown` or `known`. A crash may leave `registered` indefinitely. No client usage report can settle this server ledger.

Clients send `max_tokens`. A model policy may set `output_parameter` to `max_completion_tokens` when its fixed provider requires that spelling; the default is `max_tokens`. Validation and budget reservation use the same bounded value, and the upstream request contains exactly one of these parameters. Clients cannot select the upstream spelling or provider.

A policy can also specify `generation_model`, a canonical model ID included in its permitted response models. Admission stores this identity with the receipt, so metadata reconciliation can match a canonical name even when the chat response used a short alias. This field defaults to the requested model and is immutable across retries and later policy changes. Migration of old records defaults to their original requested model; it never guesses a canonical alias from today's policy. Canonical model mismatch keeps usage unknown.

Registration, reservation and receipt creation are one synchronous transaction. Settlement is idempotent; conflicting settlement is refused. Only a valid explicit upstream cost and token tuple can settle. Missing cost is unknown even when token counts exist. Explicit zero is known zero. Unknown reservations remain outstanding, including across day boundaries, until separately validated generation metadata can settle them. Summaries distinguish known cost, unknown reservations and request count. A reported cost above reservation freezes admission pending operator investigation.

## Recovery without inference replay

The forwarder checkpoints the first observed generation ID from an upstream header or validated response/chunk before forwarding client-visible response bytes. The checkpoint is immutable and contains no content. A failure before observing the ID can still leave an unreconcilable registered request; the implementation never guesses a generation from account-wide usage.

`POST /v1/admin/relay/requests/:server_request_id/reconcile` requires a browser administrator, the existing CSRF check and exactly `{}`. The server derives the recorded generation ID; callers cannot supply an ID, URL, model, provider, cost or token count. It performs one fixed-origin `GET https://openrouter.ai/api/v1/generation?id=...`, rejects redirects, uses a 10-second timeout and caps the response at 32 KiB. It never calls the generation content endpoint or submits a second inference. Already known records return their existing receipt without a lookup.

Both registration and provider creation must be at least 600 seconds old; provider creation must be within five minutes of the recorded request start. The metadata must identify the recorded generation and original/observed model/provider, include a terminal `finish_reason` (`stop`, `length`, `tool_calls`, `content_filter` or `error`), boolean cancellation state, explicit nonnegative `total_cost`, and native prompt/completion counts. Extra provider metadata is discarded. Missing, malformed, unmatched or nonterminal evidence keeps the reservation unknown; a 404 is never zero cost. This is a conservative evidence gate, not an independently guaranteed provider billing-finality proof.

A successful response is `{status:"settled"|"already_known",receipt}`. Reconciliation atomically updates only unknown accounting, preserves original execution outcome and request-start day, and records `usage_source:"generation"` and the reconciliation time. Concurrent finish/reconcile requests never add a second charge or replace conflicting evidence. A registered crash can have known accounting while its original execution state remains `registered`. There is no manual zero-cost override or automatic unfreeze endpoint.

## Admission expiry and finite known-accounting retention

A retained owner/ID receipt is checked before age, budget or capacity. Its duplicate/reused result never executes inference, including for legacy IDs or IDs older than the admission window. An absent ID must be UUIDv7 with an embedded Unix-millisecond timestamp no more than **30 days old** and no more than **five minutes in the future**. An absent legacy UUID, expired UUIDv7 or excessively future UUIDv7 receives HTTP **410 `relay_request_id_expired`**, with no provider call. Clients must preserve the original ID after uncertain outcomes; an expiry error is not permission for an automatic new-ID retry. This is a supported-client cutover: older companions that generate new UUIDv4 requests must upgrade.

Known accounting records expire **90 days after their latest settlement or execution-outcome update**, additionally after their embedded admission timestamp expires. A duplicate settlement does not renew retention. A late reconciliation starts a new 90-day known-record period; the original execution state can remain `registered`. Legacy known receipts can expire because absent legacy IDs are categorically rejected. The public ledger performs bounded cleanup during new admission; the private adapter schedules the next known deadline and drains additional expired rows in bounded alarm batches. No body is retained during this process.

**Unknown records and reservations remain indefinitely.** Cleanup never releases an unknown reservation, infers zero, or resets the frozen flag. Unavailable generation evidence can therefore still consume the bounded 100,000-row capacity. At capacity, new inference fails closed; retained retries remain protected. A late finish, checkpoint or reconciliation cannot recreate a purged record.

This deliberately favors spending safety over availability. Repeated failures before a generation ID is observed can accumulate unresolved reservations and eventually exhaust admission for the organization, including on later days. An authorized device can accelerate that denial of service. Revocation prevents more requests but does not prove prior requests were free. The MVP has no operator evidence-import or independently durable billing reconciliation for missing IDs; do not solve exhaustion by dropping those reservations or resetting storage. This is an explicit production availability limitation, not an anomaly detector or automatic punishment feature.

Admission, accounting updates and purge advance a persistent monotonic clock floor inside their transactions. After a server clock rollback, an old purged ID therefore remains expired, and budget admission uses the floor's JST day. Summary `admission_day` exposes that day. A major clock error can block legitimate requests; resetting the clock floor or deleting the ledger would break replay protection and is not an operational recovery mechanism.

Summary `history_complete_since` is null before any purge; afterward it is the ISO timestamp immediately after the newest deleted request start. Earlier periods can contain only partial history and must not be described as zero usage or complete totals. Retained unknown rows from older periods continue to reserve budget regardless of that history boundary. This relay retention is separate from the client monitoring event retention.

A consistent backup must preserve receipts, reservation state, frozen state, the clock floor and coverage boundary together. UUIDv7 does not reconstruct executions lost by restoring an inconsistent or stale ledger inside the still-open admission window. Do not erase or reset these records to clear capacity or reservations.

The Python 3.11 companion generates RFC 9562 UUIDv7 with cryptographic random tail bits and no machine identifier; no Python runtime upgrade is required. The public TypeScript helper and Python helper share an RFC test vector. DPoP proof IDs, sync mutation IDs, installation IDs and server correlation UUIDs retain their existing formats. [RFC 9562 UUIDv7](https://www.rfc-editor.org/rfc/rfc9562.html#section-5.7), [Python 3.11 UUID support](https://docs.python.org/3.11/library/uuid.html).

The company policy pins model aliases, provider slug/accepted response labels, model context bound, token prices, maximum output tokens, daily budget, timeout and request limits. Required upstream routing is `only` and `order` for that provider, `allow_fallbacks:false`, `require_parameters:true`, `data_collection:deny`, `zdr:true`, and `max_price` prompt/completion USD per million tokens plus request zero. No client-supplied value can weaken it. A missing eligible provider fails closed.

The reservation uses the entire pinned context bound at the prompt price cap plus requested output at the completion cap. This avoids underestimating message/tool formatting tokens. It remains local admission control, not an invoice guarantee: upstream price semantics, fees, other consumers of the API key and outdated model bounds are external assumptions. Operator account/key credit controls are also required. Price/cap changes need an explicit reviewed policy update; no automatic cheaper-provider fallback or usage-unknown-to-zero conversion exists.
