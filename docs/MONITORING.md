# Public monitoring contract 1.0.0

The executable manifest is `MONITORING_MANIFEST` in `packages/core/src/monitoring.ts`; the distributed JSON is `monitoring/manifest.v1.json`. The authenticated `GET /v1/monitoring/manifest` returns the same value. The private application pins this public module. Collection fields, validation, persistent SQL columns, projections, aggregation and retention are implemented publicly, not extended through private configuration.

Environment application status is a separate, explicitly published metadata report: [SYNC_STATUS.md](SYNC_STATUS.md) and `SYNC_STATUS_MANIFEST` declare its device-only revision ACK, server receipt timestamp, latest-only storage and owner/admin readers. It never carries content or client clocks, never turns a download into proof of application, and is not added to these immutable audit/OTLP batches. Its separate authenticated manifest endpoint is `/v1/sync/status-manifest`.

Monitoring contains only the listed activity kinds, fixed outcome/tool/model enums, counters, durations and opaque correlation identifiers. No generic text, hostname, URL, path, raw error, prompt, response, persona, skill content, tool argument/result, authentication header or cookie is accepted. Resource names and span names are fixed. A malicious client can lie about an allowed counter or encode information into identifiers; signatures do not establish device truth or binary/source equivalence. There is no anomaly scoring or automatic sanction.

## Two client transports and one separate server record

1. `POST /v1/monitoring/audit` takes an ES256 compact JWS (`application/jose`). Protected header is exactly `{alg:"ES256",typ:"myhermes-audit+jws",kid:<authenticated installation UUID>}`. Payload is canonical sorted-key JSON of `AuditBatch` (schema 1, manifest 1.0.0). The server obtains the verification key from enrollment, never from a payload key. No signing key reaches the server. Authentication supplies person and installation identity.
2. `POST /v1/monitoring/traces` takes standard **OTLP/HTTP protobuf** (`application/x-protobuf`, no compression). The Python OpenTelemetry SDK generates real spans and its official encoder generates `ExportTraceServiceRequest`. Successful response is HTTP 200 with an empty protobuf `ExportTraceServiceResponse`. This is a deliberately narrow OTLP receiver: traces only, fixed resource/scope/name and manifest attributes, no span events/links/status message. Future or unknown protobuf fields are rejected. It does not claim to be a general-purpose collector.
3. Relay executions have a separate **server-observed** ledger described in [RELAY.md](RELAY.md). Client-reported model cost is never added to that ledger. `request_id` correlates records without copying request/response bodies. Audit and OTel event counts are displayed separately; duplicate delivery does not count twice within either source.

Both client transports use fresh DPoP authentication on each attempt. Browser sessions cannot ingest events. Revocation blocks new ingestion immediately. The audit payload has immutable batch/stream/event UUIDs, contiguous sequence numbers, client timestamp, client/manifest versions and previous canonical batch SHA-256. Initial stream starts at sequence 1 with null previous hash. A matching retransmission returns the prior receipt (`status:duplicate, accepted:0`) with batch ID, hash and last sequence; a reused ID with different metadata or broken chain returns 409. A chain rejection is a validation receipt, not an intrusion diagnosis.

The server rejects an entire malformed batch before storing events. Only a fixed rejection code, transport, authenticated subject and received time is retained; no rejected payload, payload hash or exception text is retained. Accepted audit batches retain their permitted canonical metadata and signature. OTLP is stored as the public normalized metadata projection, not raw protobuf bytes.

## Inspect, export, retention

The companion's durable metadata outbox exposes the exact permitted payload for inspection. Each event is signed and encoded before transmission; audit and OTLP acknowledgements are independent. Losing a response reuses identical bytes. Queue limits, drop counters, delivery behavior and sampling are in the manifest. An expired offline chain is explicitly abandoned and a new stream starts; pending content is never silently rebased onto another chain. The client does not read whole sessions, scan user documents or auto-instrument libraries.

```sh
myhermes monitoring manifest
myhermes --state-dir /absolute/installation-state monitoring manifest --remote
myhermes --state-dir /absolute/installation-state monitoring inspect --limit 100
myhermes --state-dir /absolute/installation-state monitoring inspect --include-wire
myhermes --state-dir /absolute/installation-state monitoring export --export-dir /absolute/new-export-directory
myhermes --state-dir /absolute/installation-state monitoring flush --limit 100
```

The local manifest works without setup, authentication or network access. `--remote` verifies an exact match with the authenticated server's public manifest. Inspection includes safe pending and recent delivered events; `--include-wire` adds the signed audit, protobuf bytes and decoded OTLP fields after validating their stored integrity. Export creates a new owner-only JSON file and does not overwrite an existing export. Signing keys and access tokens never appear in these outputs.

The client stores one event per immutable batch in this MVP. Up to 10,000 pending events are retained separately from the personality/skill databases. When full, existing chains remain intact, a new metadata event is dropped, and a durable counter is reported when space becomes available. When any pending batch expires after 30 days, the entire pending chain is marked expired and a new stream starts. The count reflects incomplete logical events, including a possible audit acknowledgement with a still-pending trace. A fully delivered stream also restarts after **30 days without a new batch**, leaving margin before the server's 90-day stream-head retention expires. Client creation time and server receipt time are different clocks: an initially allowed five-minute future skew followed by correction must not cause the client to continue a server-expired chain. Idle rotation runs only when no pending event remains, preserves previously signed batches and receipt history, loses no events and increments no drop counter. It does not clear pending data in response to a chain rejection. A bounded local inspection history retains at most 1,000 delivered/expired records for at most 90 days; it contains only the same public metadata and wire payloads. Both unsigned local delivery metadata and every present protobuf field are validated before inspection/export; a newly added SDK field cannot silently expand collection.

CLI instrumentation records explicit enrollment, personality synchronization/edit/recovery, connection changes, connector reads, skill changes, runtime installation/update and managed session events. It uses fixed outcomes and durations; file paths, account labels, commands and response contents are excluded. The first signed event requires completed enrollment. Read-only inspection/history/listing and dry runs do not collect or flush metadata. Instrumented commands flush afterward unless `start --offline` was selected; `monitoring flush` explicitly retries pending work. Metadata delivery failures leave queued metadata intact, add a fixed diagnostic, and do not roll back the user's content operation. `monitoring` in normal command JSON states whether metadata was acknowledged, queued or deferred.

Owner routes are `GET /v1/monitoring/installations/:installation_id/{summary,audit,traces,rejections,batches}`. The owner may inspect all of their registered environments, including revoked ones. Administrators use `/v1/admin/monitoring/installations/...` and can retrieve only these same metadata projections. Lists are newest first, at most 100 entries and **1,048,576 bytes of serialized UTF-8 JSON**, including the envelope. `MONITORING_READ_LIMITS` publishes both limits. A complete accepted audit batch always fits alone; a batch is never split or truncated. The implementation reads a SQL cursor until the page limit and one lookahead, without materializing 100 full batches. Corrupt oversized stored data fails closed instead of bypassing the limit.

Use `?before=<next_before>` for the next page. When another record is omitted, `next_before` is the cursor of the last record actually returned; the next request selects strictly smaller cursors. A final or empty page has null. Newer records arriving during traversal do not shift the remaining pages, although ordinary retention can expire old records between reads. Pagination does not create a server snapshot. No owner override query exists. [monitoring-batches-page.v1.schema.json](../schemas/monitoring-batches-page.v1.schema.json) describes the full-batch response; its comment records the byte bound that JSON Schema cannot express. Paginated JSON is the export format; the API does not expose persona or skill contents. These read limits do not change collection, admission, stored fields or retention, so the immutable monitoring manifest remains 1.0.0.

Accepted records and stream heads are deleted after **90 days from receipt**; rejected receipts after **30 days**. A scheduled daily cleanup and cleanup on access enforce the bound. At most 100,000 accepted rows per category per installation are admitted; at most 10,000 rejection receipts are retained. No accepted event more than **30 days old**, or more than 5 minutes in the future, is ingested, preventing ancient retransmissions from recreating purged events. A public version update is required to change these defaults. Restore procedures must preserve a consistent store and retention clock.

## Operational visibility

The application event store does not collect IP or User-Agent. Cloudflare Access and edge infrastructure necessarily process connection metadata outside this store; their enabled products, access and retention must be disclosed in deployment operations. Automatic Worker observability is disabled by default to avoid unreviewed request/exception collection. Neither a template nor a private skill can extend the event allowlist. Do not enable vendor body logs, debug traces or a body-caching gateway without changing the reviewed public policy.

## Verified upstream references

- [OTLP specification 1.11.0](https://opentelemetry.io/docs/specs/otlp/) defines the HTTP/protobuf transport and response.
- [OpenTelemetry Python exporters](https://opentelemetry.io/docs/languages/python/exporters/) documents SDK exporters. This release pins SDK and official protobuf encoder 1.44.0.
- [Official trace proto](https://github.com/open-telemetry/opentelemetry-proto/blob/main/opentelemetry/proto/trace/v1/trace.proto), [common proto](https://github.com/open-telemetry/opentelemetry-proto/blob/main/opentelemetry/proto/common/v1/common.proto) and [collector trace proto](https://github.com/open-telemetry/opentelemetry-proto/blob/main/opentelemetry/proto/collector/trace/v1/trace_service.proto) define the supported field numbers. Actual SDK-produced fixtures are required in compatibility tests, in addition to malformed-wire tests.
