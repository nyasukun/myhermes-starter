# Local Hermes relay bridge — M3 acceptance and contract

The companion exposes an ephemeral `127.0.0.1` HTTP port to the owner's Hermes process. A random process-only bearer credential authenticates local calls. The bridge translates that credential into the installation's short-lived MyHermes token and fresh DPoP proof, then forwards to the configured company HTTPS origin. The OpenRouter company key never belongs in this process or its configuration. The company endpoint and accounting contract are defined in [RELAY.md](RELAY.md).

The temporary managed config also disables Hermes inline-shell preprocessing of skill text. An owner's existing `skills.inline_shell: true` does not cause shell snippets to execute during managed skill preview. Original config files and other skill settings are preserved. This does not prevent explicit user-authorized script execution or turn Hermes into a sandbox.

## Acceptance criteria, defined before implementation

| ID | Required behavior |
| --- | --- |
| B01 | Bind only `127.0.0.1` on an OS-selected port; reject absent, incorrect or duplicate local Authorization headers without any company request. |
| B02 | Forward only GET `/v1/models` and POST `/v1/chat/completions`, without query/fragment/absolute-URL targets. Upstream origin is fixed, TLS-verified and redirect-free. A separate local tool metadata endpoint is specified below and is never forwarded as LLM traffic. |
| B03 | Keep the local bearer in memory, strip it from forwarded headers, fetch/refresh a device-bound token under a concurrent refresh lock and generate a fresh DPoP proof per company request. |
| B04 | Generate UUIDv7 or preserve an explicit `MyHermes-Request-Id`. Retain a bounded in-memory canonical-body digest to UUID map for the bridge lifetime; never evict entries and accidentally re-execute. Identical retries reach the same server receipt. |
| B05 | Perform one upstream HTTP operation per local request, without automatic network/status retries. Return fixed errors and request IDs on uncertain outcomes; never fabricate/replay a previous completion body. Send `x-should-retry:false`. |
| B06 | Bound request JSON to262144 bytes, normal/SSE response total to4194304 bytes and SSE frames to131072 bytes. Reject invalid JSON, conflicting framing and unknown response media types. |
| B07 | Preserve normal responses, function tool calls and SSE bytes; stream with bounded buffering and consumer backpressure. Disconnect/timeout/bridge shutdown closes the upstream transport. |
| B08 | Never log request/response bodies, headers, token values or raw transport/provider errors. Error responses contain fixed codes and allowlisted receipt metadata only. |
| B09 | Functional synthetic HTTP tests cover concurrency, refresh, duplicate IDs, lost responses, redirects, large bodies/frames, cancellation, timeout and no credential/header leakage. |
| B10 | Integrate the pinned Hermes runtime only after checking primary, auxiliary and stream retry paths; do not infer that SDK retry configuration also disables Hermes retries. |
| B11 | The optional local tool endpoint accepts only the published tool kind, outcome and duration, with no name/content fields. Verify the actual pinned plugin dispatcher with undeclared arguments/results that cannot be inspected. |

## Deliberate limits

An ordinary OpenAI client does not always supply a stable application request ID. For such requests the bridge uses the canonical JSON request digest and retains only that digest plus a UUIDv7 with random tail bits, never the message content, after forwarding. The mapping includes successful calls, because an acknowledgement may be lost after completion. The maximum number of distinct requests is bounded (default1000); capacity exhaustion fails closed. A byte-equivalent/canonically equivalent request in the same bridge session cannot be intentionally executed again with a new ID. This favors prevention of duplicate execution over transparent replay. The Python 3.11-compatible generator uses integer milliseconds and cryptographic randomness; no host identifier or fallback to UUIDv4 is used. HTTP410 `relay_request_id_expired` stays a fixed error with `x-should-retry:false`; neither this rejection nor a changed clock renews the existing mapping. Explicit retained legacy IDs can still reach an existing server receipt, while absent legacy IDs are rejected server-side. A new bridge process does not restore these in-memory mappings; the company receipt remains authoritative for an explicitly retained request ID.

Explicit IDs are preserved. Reusing an ID for different content is rejected. A different explicit ID for a body already registered in the current bridge is rejected rather than bypassing duplicate protection. Repeated requests may receive the company's409 receipt metadata; the bridge stores no completion body for replay. Client cancellation cannot prove that the provider did not charge; missing usage remains unknown in the server ledger.

Loopback HTTP is only the local hop, authenticated by a random bearer unavailable to unrelated browser pages. There is no CORS allowance. Remote company transport requires HTTPS; explicit synthetic integration tests may enable loopback HTTP. This is not an OS sandbox against the same machine owner or arbitrary user-controlled processes.

## Pinned runtime integration boundary

Credential-isolation acceptance: the main Hermes process can read its ephemeral relay bearer, but the pinned terminal and other default child-process environment builders must remove it, including `_HERMES_FORCE_` attempts. The actual terminal shell snapshot must contain no bearer before or after a command. `MYHERMES_STATE_DIR` must remain available for the two bundled skills. This does not claim a sandbox against an owner process deliberately reading its own parent environment or disabling upstream protections.

The bearer uses `AUXILIARY_MYHERMES_API_KEY` because the verified upstream treats `AUXILIARY_*_API_KEY` as an internal secret across its default spawn surfaces. This name is a credential-storage convention, not an additional auxiliary inference task. The legacy `MYHERMES_SESSION_TOKEN` is no longer generated; inherited legacy/current names, casing variants and force-prefixed variants are removed before creating the fresh child environment. The main provider and in-process monitoring hook use the new name. The pinned terminal regression first reproduced the old bearer in an actual mode-0600 shell snapshot, then verified six child-environment variants, forced passthrough rejection, snapshot absence before/after a command and preserved `MYHERMES_STATE_DIR`. It skips login-shell initialization to avoid reading owner rc files, while using the official environment filtering, snapshot and command implementations. It makes no provider or network requests. [Official internal-secret rule](https://github.com/NousResearch/hermes-agent/blob/2237be355906fbe6065ce1815711eee52b2d646e/tools/environments/local_env_policy.py#L174), [child-environment filtering](https://github.com/NousResearch/hermes-agent/blob/2237be355906fbe6065ce1815711eee52b2d646e/tools/environments/local.py#L233).

Inspected upstream source disables OpenAI SDK retries in the primary request client, but Hermes also has its own main API retry count, stream retries and auxiliary retries. Relevant controls at commit `2237be355906fbe6065ce1815711eee52b2d646e` are `agent.api_max_retries` (1 means one attempt), `HERMES_STREAM_RETRIES` (0 disables stream retries) and `auxiliary.transient_retries` (0 disables those transient retries). These controls are complementary to stable bridge request IDs; they do not establish that every recovery/fallback path is disabled. The installed OpenAI SDK recognizes response header `x-should-retry:false`.

The launcher keeps the same Hermes home and conversation, supplies the bridge bearer through `AUXILIARY_MYHERMES_API_KEY`, and uses the official `HERMES_MANAGED_DIR` overlay to configure a named `myhermes` provider with `key_env` and the ephemeral loopback base URL. It pins the main and auxiliary provider/model to `myhermes`/`economy`, disables configured fallback models, and sets the retry limits above. Existing owner config bytes are preserved. The overlay is JSON (valid YAML) in a temporary `0700` directory with a `0600` config file. It contains routing metadata and an environment-variable name, never the bearer value. Normal exit and Python exceptions remove the overlay. A hard kill can leave a secret-free overlay directory under `.myhermes-runtime`; it is outside the personality synchronization allowlist and does not retain usable credentials.

The pinned auxiliary inventory is explicit. Its 18 default task blocks are `vision`, `compression`, `skills_hub`, `approval`, `review`, `mcp`, `title_generation`, `memory_query_rewrite`, `tts_audio_tags`, `triage_specifier`, `kanban_decomposer`, `profile_describer`, `goal_judge`, `curator`, `monitor`, `background_review`, `moa_reference` and `moa_aggregator`. The launcher also pins three implemented names absent from those defaults: core `/btw` uses `side_question`, the shipped Kanban plugin uses `kanban_estimator`, and the shipped Teams pipeline uses `call`. Adding their routing blocks does not enable the optional plugins or cause inference by itself. Automatic title generation remains a separate inference request when enabled; its usage goes through the same relay.

The 21-slot regression runs the actual pinned `load_config_readonly` and `get_text_auxiliary_client` against synthetic owner configurations that name a different endpoint/model/key. DNS and socket connections are prohibited. Every client resolves to the local relay, `economy` and the process credential; the actual `/btw` fork resolver also retains the managed parent runtime. Before the fix, `side_question`, `kanban_estimator` and `call` retained the owner-configured endpoint. No model request is made by this probe.

This controls the known task configuration slots. Arbitrary plugin-defined auxiliary names remain outside that inventory, and code-level explicit provider/model arguments take precedence in the upstream auxiliary API. For example, MoA slot code can supply explicit routing arguments. The launcher does not sandbox owner code, prohibit plugins or claim to force every possible custom inference path through the relay. Such extensions need their own integration review. Their presence does not create a new approval step for ordinary registered personal connections.

The child environment excludes case-insensitive `OPENROUTER*`, `OPENAI_*`, `ANTHROPIC_*`, `LANGFUSE_*`, `HERMES_LANGFUSE_*` and `OTEL_*` variables and stale Hermes routing/profile overrides. The overlay disables upstream shared-metrics collection/transmission; MyHermes emits its published explicit metadata only. It prepends the companion virtual environment to `PATH` when the companion executable exists, and supplies `MYHERMES_STATE_DIR` so packaged runtime skills address the same registered environment. The process credential does not appear in a command argument.

The pinned dotenv loader has no supported option that prevents all dotenv and external-vault loading. Managed startup therefore refuses an existing `.env`/`.op.env` in the Hermes home, `.env` in the upstream checkout, external `secrets` configuration, or an owner-defined provider using the reserved `myhermes` name. It reports a remediation without reading dotenv values, copying credentials or removing owner files. Back up and migrate such setup explicitly before managed launch. `start --offline` only skips synchronization; model calls continue to require the company relay and fail safely without network access.

## Tool and model monitoring

When a monitoring callback is supplied, POST `/v1/myhermes/tool-events` accepts at most 1024 bytes of JSON with exactly `tool_kind`, `outcome`, and `duration_ms`, authenticated by the same process-only bearer. It applies the public monitoring validator and passes only those attributes to the parent process's explicit instrumentation. It never makes a company LLM request. No CORS, redirect, arbitrary target or body logging is enabled.

The public `hermes_monitoring_plugin.py` is installed as fixed source under `HERMES_HOME/plugins/myhermes-monitoring`. The temporary managed overlay enables it alongside existing explicit plugin opt-ins. Its `post_tool_call(tool_name, duration_ms=0, status=None)` signature deliberately has no `**kwargs`: pinned Hermes removes undeclared arguments, results, error text and IDs before invocation. Known tool names are mapped to a small fixed category table; unknown names become `other`. Only category, normalized outcome and bounded duration cross the local endpoint. The callback never transmits names or tool content. It has a 250 ms transport timeout and no retries; client-reported monitoring may therefore be incomplete and cannot establish that unreported activity did not occur.

Installation preserves a differing pre-existing plugin and rejects startup rather than overwrite it. Exact public plugin source can remain installed after exit or a hard kill; it contains no credential and is enabled through the temporary overlay. Startup rejects extra files, symlinks, hardlinks and modified source in that reserved directory. The child disables Python bytecode writes so unverified cached bytecode is not created there. This is transparent process instrumentation, not protection against the machine owner changing code at runtime.

The relay callback emits client-reported `model` events with normalized outcome, duration, original request ID, the allowed model alias when known, and observed nonnegative prompt/completion counts when supplied by the response. It never infers missing tokens/cost or copies provider errors. Repeated local attempts may produce repeated client-reported activity events; the separate company receipt/ledger remains authoritative for execution and accounting. `runtime_start` and `runtime_stop` surround the actual child process. Callback failures do not expose exception text or block owner work.

Synthetic HTTP bridge checks cover child launch/exit/cancel records, a child process calling the bridge, the actual pinned upstream config/provider resolver, and plugin discovery/dispatch with hostile undeclared argument/result fixtures. Run `MYHERMES_TEST_UPSTREAM=/path/to/pinned/hermes .venv/bin/python -m unittest discover -s tests -p 'test_*relay*.py' -v` for those paths and `MYHERMES_TEST_UPSTREAM=/path/to/pinned/hermes .venv/bin/python -m unittest discover -s tests -p test_runtime_auxiliary.py -v` for the 21-slot probe. Without an explicit upstream path, official-runtime probes are skipped. Local synthetic results do not establish live provider acceptance; OS evidence is recorded separately in [OS_CHECKS.md](OS_CHECKS.md).
